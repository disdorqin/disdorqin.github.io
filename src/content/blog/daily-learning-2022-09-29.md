## 一、为什么编译器的第一步不是把代码直接转换成机器指令？

假设你写出一句最简单的程序：给变量 count 赋值十，然后让它加一。人类看一眼就明白，count 是变量、十是数字、加号表示算术运算。但对计算机而言，最初得到的是一串字符：字母、数字、空格、冒号、等号和分号混合在一起。它们的边界、类别和意义都不是操作系统天然知道的。我们必须先约定一套语言规则，才能把字符序列解释成程序。

编译器的前端通常分成几个逻辑阶段。词法分析负责将字符分组为 Token；语法分析判断 Token 是否符合语言的结构规则并组织成语法树；语义分析检查变量作用域和类型等约束；后面可能还有中间表示、优化和代码生成。工业编译器的具体组织可能更复杂，也可能融合其中几步，但对学习者而言，先分别理解每个阶段的输入输出，是避免概念混乱的最好方法。

词法分析为什么适合作为入门？因为它没有必要立即理解整个程序的语义。即使编译器不知道 count 是否已经声明，也能够识别它符合标识符的词法规则；即使不知道加法最终用哪条 CPU 指令实现，也可以识别加号是运算符。我们先解决字符如何构成一个个词语的问题，再去处理这些词语如何构成表达式与语句。

这种分层还能简化调试。例如出现没有结束的字符串字面量，通常可以在词法阶段报告；出现多了一个右括号，应当由语法分析来报告；出现调用一个未声明的变量，通常需要语义阶段检查。若所有判断都堆在一个巨大的字符处理循环里，错误类型、位置和恢复策略会纠缠在一起，维护困难也会随语言功能增长而加剧。

理解编译器最好从“字符不是指令”这句话开始。字符流需要经过一系列形式化转换，逐步获得结构和意义。词法分析就是第一道转换：它把人类看起来连续的程序文本，变成下一阶段能够稳定消费的 Token 流。随后才有机会谈论解释执行、代码生成、优化和虚拟机。

## 二、Token 与词素有什么区别？为什么还要保留位置？

考虑一行教学用代码：count := 10; 。我们希望扫描器输出四类词法单元：标识符 IDENT、赋值符 ASSIGN、整数 INTEGER、分号 SEMICOLON。count 与另外一个变量 total 的 Token 类型都可能是 IDENT，但它们的原始文本不同；数字 10 和 0010 的整数值可能相同，但源文本表示不同。因此，只保存 Token 类型会丢失很多信息。

词素 lexeme 指当前 Token 在原始程序中对应的字符子串。例如词素 count 是五个字符，而 INTEGER 类型的词素可以是 10。Token 的字面值可以是进一步转换出的整数十或浮点数十点五。源位置则记录起始与结束的行、列或偏移。一个实用 Token 对象至少要让后续阶段能回答：它是什么类型、原文是什么、可选值是什么、从哪里来。

为什么错误位置信息需要从一开始维护？设想源程序第三行写了错误的数字格式，词法分析器若只返回“发现无效数字”，使用者仍要在整个文件里猜测位置。若后续阶段发现表达式缺少分号，解析器也需要知道最近 Token 的源位置才能给出准确提示。位置不是美化输出的功能，而是扫描器与解析器的共同接口。

还存在一种常见疏忽：一个制表符究竟算一列，还是显示时跳到下一个制表位置？中文字符在 UTF-8 下占多个字节，但在代码编辑器里通常不是多个普通英文列宽。对于课程实验，可以明确规定列号按字符计算；如果项目要与 IDE 的诊断协议对接，就需要认真选择字节偏移、Unicode 码点索引和显示列的含义，避免中文注释之后的错误定位全部偏移。

此外，空格与注释不一定被直接丢弃。普通编译器可以将空白跳过，但保留换行用于位置计算；格式化工具可能需要原始注释和空白来恢复文件布局。一个标记有类型、原文和跨度的 Token，比只有类型数字的 Token 更适合扩展。然而扩展多少字段应取决于任务，不需要为了简单实验提前设计复杂的元数据系统。

## 三、最长匹配：为什么 ifelse 不是两个关键字？

假设语言规定 if 和 else 是关键字，标识符由一个字母开头、后跟零个或多个字母和数字。输入 if 时，标识符规则与关键字规则都能匹配；语言通常希望输出 IF。输入 ifelse 时，即使开头两个字符构成 if，我们却希望整个六字符词素属于一个标识符，而不是把它切成 IF 和 ELSE。决定这个行为的关键不是高级机器学习，而是精确定义的词法优先规则。

常见扫描器首先采用最长匹配：从当前字符位置开始，寻找某一种模式能够接受的最长前缀。若多种模式得到同样长度，再按照事先规定的规则优先级选择 Token 类别。因此，在 ifelse 这个例子中，标识符匹配长度六，关键字 if 只匹配前两个字符，前者获胜。在 if 这个例子中，两种模式匹配长度都是二，关键字的优先级较高，因而输出 IF。

手写实现还有一个非常自然的策略：只用一条标识符规则读完所有连续字母和数字，然后查询该完整词素是否出现在关键字表。如果命中，则返回对应关键字；否则返回普通 IDENT。这等价地实现了本例需要的行为，但前提是语言对保留字和标识符的规则确实如此。对于上下文相关的语言或特殊前缀规则，仍可能需要更复杂的处理。

另一个典型例子是大于号与大于等于号。若输入是 >=，在读到 > 时扫描器已经看到一个合法运算符，但它不能立即停止，因为后面还有 =，两个字符合在一起是更长的合法 Token。实际实现可以通过向前看一个字符完成，也可以让 DFA 继续行走并记住最近一次接受状态，直到无法延长后再决定。

这也解释了为什么必须区分“出现过接受状态”和“当前仍能继续匹配”。扫描器可能先经过一个合法词素，随后尝试更长模式失败，此时应该返回先前的最长合法结果，并把多读的字符留给下一 Token。无论使用手写分支还是自动机状态表，这个细节都会影响程序的正确性。

## 四、正则表达式并不是所有程序语法的万能描述工具

正则表达式的数学含义，是用一组有限的构造规则描述某些字符串集合。我们先定义两个字符集合：L 代表所有允许的字母，D 代表所有数字。标识符规则可以描述为开头一个 L，后面跟零个或多个来自 L 或 D 的字符。用形式语言符号表达如下：

$$
\mathrm{IDENT}=L(L\cup D)^*.
$$

这里的并集表示“二选一”，星号表示任意次重复，包括零次，紧邻的表达式表示连接。所以 a 属于该语言，a12 也属于它，而 12a 不属于它。这个表达式不是一行能够直接运行的 Python 代码，而是定义一个允许字符串集合的形式化规则。后面我们将用算法把这个定义转换为识别程序。

经典正规表达式主要由选择、连接、重复及其派生缩写组成。它们适合识别标识符、数值、简单字符串内容和运算符等局部模式。可如果要描述任意深度的匹配括号，有限状态机一般无法记住无限多层尚未闭合的左括号。这类递归结构通常由上下文无关文法、递归下降解析器或栈来处理。

举例来说，输入 (((a))) 包含三层括号，我们希望任何有限深度的合法嵌套都被允许。固定有限个状态不能为所有可能深度分别保存一个计数。编译器不需要让词法分析器在第一步解决它，而是分别返回左括号、标识符和右括号 Token，再由语法分析根据嵌套规则组织结构。这就是为什么编译原理会把正则语言和上下文无关文法分在不同章节。

还要注意，在实际编程环境里叫作 regex 的库可能提供反向引用或各种回溯扩展，并不与这里的经典正规语言完全一致。我们谈“正则表达式自动变成 DFA”时，限定的是经典可由有限自动机识别的规则。理解这个边界，能避免把所有字符串处理问题都错误地归结成有限自动机。

## 五、DFA：一个明确的状态加一个输入字符，只能有一个后继

确定性有限自动机 DFA 可以理解为一个只有有限数量状态的识别器。它有状态集合 Q、输入字母表 Σ、转移函数 δ、起始状态和接受状态集合。对给定状态与输入符号，转移函数决定唯一的下一状态。若转移没有显式写出，可以用进入死状态表示无法继续合法匹配。所谓确定性，与模型有没有随机数没有关系，只是同一步不存在多个可选路径。

我们先定义一个极简单的语言：输入必须先出现一个 a，之后可以出现任意多个 b。起始状态 q0 遇到 a 后进入 q1，q1 是接受状态；q1 再读 b 时保持在 q1。输入 a、ab、abb 都合法，输入 b、ba 和 abba 不合法。这一台机器识别了无限多个长度各异的字符串，但内部只有很少的状态。

执行过程非常直接：从 q0 出发，逐个字符查转移表，直到输入结束，再检查当前状态是否接受。若 DFA 已经构造好，读取每个字符通常只需一次固定成本的状态查表，因此对长度 n 的输入有 O(n) 量级的识别成本。这里讨论的是运行阶段，不能据此断言从任意正规表达式构造 DFA 的状态数一定很小。

如果输入是 abbx，当扫描器读到 abb 时仍处于接受状态，随后遇到 x 无法继续。若任务是判断完整字符串是否属于 a b*，答案是“不属于”；如果任务是扫描连续代码流，扫描器可能应该返回 abb 这个最长合法 Token，再把 x 留给后续扫描。这两种应用场景看似相近，却有不同的终止条件，千万不要混淆。

DFA 的优点是运行路径简单，不需要为每个字符维护一组可能状态。但在某些输入模式下，等价 DFA 可能拥有远多于原始 NFA 的状态数，最坏情况存在指数级增长。工程上通常需要在构建成本、状态表大小和运行成本之间做权衡，而不是机械地认为每一种规则都必须预先最小化成唯一最小 DFA。

## 六、NFA：非确定性不是“随机猜测”

非确定性有限自动机 NFA 允许从同一状态读同一个字符时有不止一个后继，也可以沿不消耗字符的 ε 边发生转移。识别规则是：只要存在一条路径能够消耗整个输入，并最终进入接受状态，输入就被接受。这里的存在性是数学条件，不表示软件运行时必须调用随机数猜路径。

设一个起始状态可以沿 ε 边进入两条分支，一条读 b，另一条读 c。若输入 b，只有 b 分支能继续并最终接受；若输入 c，另一条分支能接受；输入 a，两条分支都无法消耗，因而拒绝。计算机可以维护一组“目前可能处于的 NFA 状态”，一次处理所有可达状态，完全无需盲目尝试或者复制很多独立进程。

NFA 非常适合以积木方式描述正则规则。要表达两个模式相连，就让第一个模式的接受位置连接第二个模式起点；要表达或，就让一个新起点沿 ε 进入两个分支；要表达零次或多次重复，就让接受路径能够回到起点，同时允许完全跳过。Thompson 构造的核心思想就是使用这些小部件，按照表达式结构组合出整体 NFA。

为什么还需要把 NFA 转成 DFA？因为 NFA 的多个可能状态集合，可以通过一个确定性的集合状态统一表示。实际词法生成器可以提前计算这种转换，之后只做普通状态查表。也可以直接模拟 NFA 或按需缓存集合状态。二者并不代表两类不同的语言能力：在经典正规语言范围内，它们具有相同的识别能力，只是实现方式和资源开销不同。

## 七、手把手构造 a(b|c) 的 ε-NFA

我们选择最简单但有完整分支的表达式 a(b|c)。它只接受 ab 或 ac，不接受 a、abc 或 ba。为方便推导，给状态命名：q0 起点，读 a 到 q1；q1 沿 ε 到 q2 或 q4；q2 读 b 到 q3，q4 读 c 到 q5；q3 和 q5 通过 ε 到唯一接受状态 q6。这是一个合理的教学 NFA，不要求与特定工具内部编号完全相同。

实际验证输入 ab 时，读 a 后到达 q1。由于 q1 可以不消耗输入沿 ε 走到 q2 或 q4，我们同时考虑状态集合 {q1,q2,q4}。下一字符 b 只能从 q2 分支读入，进入 q3，再经过 ε 到 q6，因此输入结束时可以接受。若输入 ac，则改走 q4 的 c 分支，同样达到 q6。

输入 abc 时要格外注意。读完 ab 的确可以到达接受状态 q6，但作为“整串匹配”任务，后面还有一个 c 需要消耗。此时无法继续，因而应该拒绝整个 abc。只有当词法分析器的任务变成“从当前位置取最长合法 Token”，才会把 ab 视为能够单独输出的 Token 前缀。

现在想一想，如果表达式改为 a(b|c)*，会发生什么变化？星号允许分支重复零次或多次，a 本身也成为合法输入，abccbc 同样可能合法。我们只需在现有分支结构上增加用于重复和跳过的 ε 转移，不必从头编写识别器逻辑。这种组合性使自动生成成为可能，也是形式语言与工程连接的重要一环。

## 八、子集构造：为什么每一组 NFA 状态可以被当作一个 DFA 状态？

子集构造依赖两个集合操作。move(S,x) 表示从集合 S 中任一状态读取字符 x 后可直接抵达的状态；ε-closure(S) 表示从 S 出发，经过零次或多次 ε 转移能到达的全部状态。对于 DFA 当前状态 S，读入 x 后的下一状态由这两个操作组合决定：

$$
\delta_D(S,x)=\varepsilon\text{-closure}\bigl(\operatorname{move}(S,x)\bigr).
$$

公式并不复杂：先消耗一个字符，再把所有不消耗字符的免费转移走完。这样一来，对固定集合 S 和输入 x，得到的集合一定由确定的集合运算给出，因此整个 DFA 转移是确定的。起始状态是原 NFA 起点的 ε-闭包；某个集合只要包含原 NFA 的接受状态，就成为 DFA 接受状态。

继续使用 a(b|c) 的例子。第一个 DFA 状态 A={q0}；读 a 后得到 B={q1,q2,q4}；从 B 读 b 得到 C={q3,q6}；从 B 读 c 得到 D={q5,q6}。C 和 D 都是接受状态，因为它们都包含 q6。其他不合法转移进入空集合或死状态。由此，我们已经用四个可达集合状态描述了原 NFA 所识别的语言。

NFA 的不同实现可能给出不同状态编号与中间集合，但转换原理相同。实际算法可以用一个队列保存尚未展开的集合状态，每取出一组，就对输入字母表的每个字符计算后继集合。如果新集合从未出现，就给它分配新的 DFA 状态编号并加入队列；一直循环直到全部集合处理完成。这里没有一步需要“理解”语言业务，也不需要大语言模型。

这一算法的意义非常深：一份声明式规则可以经过已知的数学变换，变成确定可执行的状态表。代码生成器可以把表写成数组，或者把每个状态的转移翻译成 switch 分支。于是“写规则生成代码”不是什么人工智能奇迹，而是由有限状态语言性质支撑的程序变换过程。

## 九、为什么 DFA 最小化可能有用，却不是唯一重点？

子集构造得到的 DFA 可能存在冗余状态。假设两个状态在未来接收任何后续字符串时，接受与拒绝的结果总相同，那么从语言识别角度看，它们没有必要区分。最小化算法会识别这种等价关系，并在保持识别语言不变的前提下合并状态。

在 a(b|c) 的例子中，C 与 D 读完合法输入时都接受，之后若对其他输入行为完全相同，就有机会合并。特别注意，工业词法生成器不只关心“是否接受”，还关心接受后应当输出哪个 Token 类型和执行什么动作；如果两个状态对应不同 Token 动作，就不能仅因都接受而随意合并。

为什么有时不值得专门最小化？若语言只有少量词法规则，DFA 状态很少，运行速度已经满足要求，那么继续做复杂优化的收益有限。更重要的是先保证最长匹配、优先级、出错位置、输入缓冲和 EOF 行为正确。对于非常大的规则集合，状态表压缩可能有助于内存与缓存局部性，但也应通过实际基准测试判断是否值得。

因此，学习顺序应该是先获得正确识别器，再比较不同实现的成本。不要为了让状态数漂亮而提前省略必要语义信息，也不要认为一个扫描器状态越少就一定越快。状态布局、分支预测和实际输入分布也会影响性能，形式语言等价与工程性能是两个不同维度。

## 十、多个 Token 规则如何合并成完整的词法分析器？

真实词法规则会同时包含标识符、整数、浮点数、运算符、分隔符、空白和注释。生成器可以为每一种规则建立单独 NFA，再构造一个共同起始状态，通过 ε 转移进入所有规则的起点。随后对这个合并 NFA 执行子集构造，得到一台能够同时识别多类 Token 的 DFA。

但是能够同时识别，未必能够唯一决定 Token 类别。比如 if 符合关键字与标识符两种规则，需要根据同长优先级进行选择；ifelse 虽然前两个字符也匹配 if，完整标识符更长，因此根据最长匹配优先选择整体词素。实际生成器要把接受状态所对应的规则编号与动作记录下来，才能在多个模式之间做出确定决定。

实现最长匹配时，一个很常见的技巧是保存“最后一次到达接受状态的输入位置”和“当时应当选择的规则”。扫描器持续尝试更长的前缀，一旦没有合法转移，就返回最后记录的最长有效匹配，同时恢复必要的输入位置。如果从起点到失败位置一直没有进入过任何接受状态，则应报告词法错误。这个小机制，实际上把最长匹配语义落实到了可执行程序里。

对于空白、注释等不必进入普通语法分析的内容，识别之后可以直接执行跳过动作，但不能忽略它们对行列号和错误位置的影响。词法器的职责不是简单地“删空白”，而是先识别哪些字符在什么上下文中属于可跳过内容。例如字符串字面量内部的空格不能随意删除，注释边界也需要按语言规则识别。

这个完整过程体现了三层抽象：开发者通过正规模式声明词法语言；自动机算法把这些模式转换为状态转移；运行时代码根据最长匹配和优先级产出 Token 与位置。学会分清这三层，读 JFlex、Lex、Flex 或其他生成器的源码就不会感觉它们在凭空创造程序。

## 十一、一个最值得做的边界实验：为什么 10..20 不一定是浮点数？

设想一种小语言同时支持整数、小数和范围符。整数是连续的一位或多位数字；小数要求数字、小数点、再至少一个数字；范围符是两个连续的小数点。输入文本 10..20 时，符合我们语言定义的 Token 应依次是整数十、范围符和整数二十。这个例子简单，却会暴露数字扫描器中的多种典型错误。

如果程序看到 10 后面的第一个点，就不加判断地吞入浮点数词素，便可能错误地得到 10.。但按本例的语言规则，小数点后面必须有数字，所以 10. 并非完整合法的小数。扫描器应停在整数十，保留小数点作为下个 Token 的起始字符；随后两个点满足 RANGE，最后的 20 再作为整数识别。你可以手工逐字符推演，而不需要借助任何高级框架。

这里有个特别重要的条件：如果语言允许尾随点，例如 10. 也是一个合法浮点数，那么纯粹的最长匹配可能产生不同结果。因此，发现 10..20 被错误分割，不能只凭直觉责怪代码；首先要检查数值语法、范围符和词法优先级是否在规范里说清楚。不同语言对这些情形可以作出不同规定。我们这篇文章的演算只适用于开头写明的小语言。

更完整的测试集合应包含 10.20、10..20、10.、10.2.3、.5、0..0、换行之后的数字和文件结束处的数字。对于每个输入，先把预期的 Token 序列写出来，再运行扫描器比较。不要让程序先生成输出，然后拿输出反过来“定义”语言规范。前者是基于合同的检验，后者只是对已有实现的无条件接受。

这项实验还有一个科研方法上的启发：有意义的边界样本通常比大量平凡样本更能解释系统行为。连续一万个普通整数都扫描正确，不能证明小数与范围符不会发生歧义；一组精心构造的边界测试，反而能直达最容易出错的规则交界处。这是形式语言学习与软件测试共同遵循的思想。

## 十二、从规则到可运行程序：一份小而完整的扫描器结构

课程实验中，手写词法分析器完全有价值。最简单的实现可以保存源文本、当前位置、行号、列号和一个 Token 输出列表。主循环先检查是否结束，再读取当前字符。字母进入标识符识别分支，数字进入数值识别分支，空白负责更新位置，已知标点符号与运算符按规则返回 Token，其他字符触发错误处理。

下面不是某种编译器唯一正确的实现，而是为了说明职责而设计的伪代码。它没有处理所有 Unicode 字符、字符串转义或注释扩展；真正用于项目时必须补全这些条件。

    while input_not_finished:
        skip_whitespace_and_update_position()
        if is_letter(next_char):
            emit(scan_longest_identifier_then_keyword_lookup())
        elif is_digit(next_char):
            emit(scan_number_with_decimal_rules())
        elif next_two_chars == "..":
            emit(RANGE)
        elif next_two_chars == ":=":
            emit(ASSIGN)
        elif known_single_symbol(next_char):
            emit(single_character_token())
        else:
            report_error_with_location()
    emit(EOF)

读这段伪代码时不要只盯住分支顺序，而要想清每个函数的输入输出。标识符分支要消耗尽可能长的字母数字序列，完成后查关键字表；数字分支要维护至少一个可接受的整数前缀，再判断是否存在完整小数部分；运算符分支要保证对双字符词素的判断不会吞掉不属于自己的字符；遇到无法识别的字符时要保留位置。

如果用自动机生成器替换手写扫描器，这些职责仍然存在，只是“哪个字符之后走哪条分支”由 DFA 的状态转移表负责。你甚至可以把手写条件分支理解为一种直接编码的状态机。自动生成工具并没有发明新的语言意义，而是把我们声明过的规则机械转换成运行时能够执行的决策。

此外，是否在识别阶段立即把字符数字转换为机器整数，是另一项独立设计。词法合法性与数值范围不同：一个由很多数字构成的词素可能完全符合整数语法，却大到无法放入某种机器整数。遇到这种情况，应该保留原词素并执行明确的溢出检查，而不能仅因为字符合法就默认数值转换安全。

## 十三、错误位置：为什么扫描器多看一个字符之后不能随便回退？

最长匹配常常需要前瞻。为了判断大于号后面是否跟等号，扫描器可能多读取一个字符；为了判断整数后面是否构成小数，扫描器也需要查看下一个字符。如果每次“查看”都立即增加当前列号，随后发现该字符不属于当前 Token 时却只恢复字符指针、不恢复位置，接下来所有 Token 的错误位置都会发生偏移。

因此，输入操作最好分成查看和消费。查看下一字符并不改变正式读取位置；只有确定这个字符被当前词素消费时，才真正推进指针和位置信息。某些实现也允许先读再回退，但必须确保字符指针、行列信息和缓冲状态一起恢复，不能只回退其中一项。对课程初学者而言，明确区分 peek 与 advance 是一种非常划算的工程习惯。

换行也会产生特殊问题。不同系统或文件可能使用单个换行符或回车换行组合；若扫描器对回车和换行分别增加行号，错误信息就可能从第二行开始系统性偏离。可以在输入层统一换行表示，但如果后续还需要原始文件的字节偏移，则应保持原始位置与标准化位置之间的映射。

对于中文注释和非 ASCII 标识符，还要区分字节数、字符数和显示宽度。UTF-8 中一个中文字符通常不等于一个字节；某些符号在终端显示时占多列。编译器面向用户报告的位置语义应保持一致。如果只是课堂演示，可以在文档里说清列号按什么规则定义，而不是把一个不稳定的实现结果当作普适惯例。

错误恢复不是越复杂越好。简单扫描器遇到非法字符时可以立即停止；IDE 更可能希望一次报告多个错误，因而跳过非法片段后继续。但恢复时跳过多少字符必须有明确规则，否则一次非法输入可能导致后面大量合法 Token 被误吞，产生充满噪声的语法错误。这里最重要的仍是可预测行为与清楚的边界。

## 十四、EOF 不等于读取到了字母 E、O、F

任何读取循环最终都会遇到输入结束。EOF 是扫描器用来告知下一阶段“后面没有更多 Token”的协议状态，而不是文件中必须存在的三个普通字符。一个语法分析器反复获取 Token，如果扫描器在文件结束后继续返回上一次的值，就可能无限循环；如果把没有初始化的字段当作结束标志，可能出现随机行为；如果直接读取越界，则可能崩溃。

最基本的测试是空输入。一个稳妥的扫描器即使没有任何字符，也应该安全地产生结束状态。第二个测试是文件最后没有换行；第三个是文件只包含空白；第四个是合法 Token 紧接文件结束。这些输入经常暴露 off-by-one 错误，即程序误把“最后一个真实字符的位置”和“第一个不存在的字符的位置”混为一谈。

EOF 在错误报告中也很重要。假设字符串字面量已经出现开头引号，却一直没有遇到合法的结束引号。到达文件尾时，程序应该报告“字符串在文件结束前未闭合”，并指出它从哪里开始，而不是擅自把文件结尾当成结束引号。类似地，若一个双字符运算符只读到了第一个字符，语言没有定义单字符版本，则应报告不完整词素。

C/C++ 风格输入函数的一些接口还需要特别区分整型 EOF 返回值和普通字符。把 EOF 值过早强制转换到窄字符类型，可能导致与合法字节值混淆。对于课程实验，先通过合适的类型和边界判断就能避免很多隐蔽问题；对于大型编译器，还需考虑编码层、缓冲与并发读取。

这提醒我们：一个 DFA 在数学上能够识别某种语言，并不自动保证真实文件读取过程可靠。形式化识别解决的是字符序列的合法性；工程接口还需保障输入耗尽、异常、内存边界和下游调用稳定性。两部分都通过检验，才算一个真正可用的词法分析模块。

## 十五、注释、字符串和嵌套：为什么有些规则需要增加词法状态？

普通空格与注释在语法分析阶段往往不直接出现，却仍应被正确识别。单行注释通常从特定符号开始一直持续到行末；多行注释需要匹配一个结束标志；字符串字面量内部的空格、加号和其他标点则通常应作为文本内容，而不是新的独立 Token。如果扫描器不区分当前所在的词法环境，便可能把字符串中的字符当作真正的代码。

一种常见解决方式是引入词法状态。例如普通状态 NORMAL 中遇到双引号进入 STRING 状态，接下来按照字符串规则读取，直到遇到合法关闭引号再退出。遇到注释开头则进入 COMMENT 状态，在那里很多普通代码运算符不再具有原来的意义。词法状态是对扫描器行为的明确限制，不是任意增加新的机器学习模块。

如果语言允许嵌套多行注释，那么只寻找第一个结束标志就可能不够。编译器需要记录注释嵌套深度，遇到内部新注释开头时加一，遇到关闭符号时减一，到零才退出。若嵌套深度没有固定上界，这种行为就超出普通有限状态表示的直接能力，需要额外计数或其他处理。因此不要把“支持多行注释”和“支持任意深度嵌套注释”写成同一个特性。

字符串转义也会引入类似边界。例如遇到反斜杠后，下一个引号可能不代表字符串结束，而是字符串内容。扫描器必须区分普通引号和被转义的引号。若使用正则规则描述字符串，也要精确处理转义序列的合法性，不能简单写成“从一个引号匹配到下一个引号”，否则会在真实程序上过早停止。

这些例子表明，形式语言和自动机理论是认识扫描器的起点，但完整语言实现通常会额外加入状态、动作、错误处理与语义约束。理解什么由正规规则处理、什么由附加状态或后续阶段处理，比强行把所有功能塞到一条复杂正则表达式里更可靠。

## 十六、完整手推三条输入的 Token 列表

第一个输入是赋值语句 x := 10;。从 x 开始，扫描器认出合法标识符，词素为 x，返回 IDENT；空格更新当前位置；两个字符 := 返回 ASSIGN；后面 10 返回 INTEGER，最后分号返回 SEMICOLON。即使当前语法分析器还不知道 x 是否声明，词法分析也可以独立完成这个结果。

第二个输入是条件片段 if x >= 0。从 i 起连续读取字母后得到词素 if，查保留字表后返回 IF；x 返回 IDENT；由于大于号后面是等号，最长匹配产生 GE；最后零返回 INTEGER。若将 if 改成 ifx，完整词素不在关键字表里，就应返回 IDENT(ifx)，而不是 IF 与 IDENT(x) 两个 Token。这两个输入是检验关键字与标识符冲突的最小对照。

第三个输入是范围片段 10..20。按本课约定，小数必须在小数点后有数字，因此第一个点不能合法地成为 10 的小数部分。扫描器返回 INTEGER(10)，再从第一个点识别 RANGE(..)，最后返回 INTEGER(20)。若你运行程序后得到不同答案，应检查语言规则、最长匹配实现和输入回退，而不是立即针对这个字符串加一个特殊硬编码分支。

把三个案例放在一张测试表中，可以分别验证标识符识别、关键字优先、双字符运算符、数字边界、范围符和位置维护。随后再增加空文件、非法字符、没有结尾换行以及注释与字符串内容，才算把最容易出错的接口边界逐步覆盖。测试数量多并不是目的，覆盖不同失效机制才是目的。

## 十七、词法生成器如何把正规规则变成源码？

现在可以真正解释“算法自动写代码”的含义。一个 Lexer 生成器首先接收一份声明式规范，其中包含多个正规表达式和它们匹配成功后的动作。它解析规范后，为每个规则建立自动机片段；把多个片段通过共同起点整合；再做子集构造形成 DFA；必要时压缩状态或进行最小化；最后生成状态表或者包含分支判断的目标语言程序。

关键在于每一层的输入和输出都有可定义的数学关系。正规表达式描述什么字符串可以被接受，NFA 通过状态路径表达同一集合，DFA 用确定转移表达同一集合，最终代码执行 DFA 逻辑。工具并不需要理解“变量”“循环”“机器学习训练”等业务概念。它处理的是我们声明好的有限模式，再依照算法产出等价的识别器。

输出源码可以采用表驱动形式：一个状态编号，加当前输入字符索引，查询下一状态。也可以把状态转移编码成条件判断。不同方式在代码大小、构建时间和运行速度方面可能存在差别。工具还能增加 Token 优先级、动作和输入缓冲相关代码，但这些都要来自规范或者工具预设的机制，不能凭空替语言设计者决定语义。

这个过程与现代的自然语言 AI 编程有一个重要区别：经典词法生成器在明确约束的正规语言范围内，可以围绕语言等价性建立数学保证；大语言模型根据自然语言需求生成代码时，需求往往不完整，生成结果需要进一步执行、测试和审查。两者都可能输出源码，但不应该因为外表相似就混淆工作机制。

可以把生成器看作一种局部编译器：它的输入不是一般程序，而是一套词法规则；它的输出不是机器指令，而是一个识别规则的程序。这样理解之后，未来学习语法分析器生成器、SQL 查询优化器或者某些代码生成模板时，就更容易看到同一类“声明目标结构—转换表示—生成可执行过程”的思想。

## 十八、工业性能与教学正确性：哪些优化应当最后再考虑？

固定 DFA 的运行通常能以每字符一次或有限次转移完成识别，具有很好的复杂度性质。但这不意味着整个词法扫描的成本永远只是常数乘以字符数。程序还要读取文件、解码文本、维护位置、构造 Token 对象、转换数值与处理错误，某些实现还可能反复分配临时字符串。实际性能要通过代表性输入测试，不能只引用一个理论复杂度就宣布最快。

子集构造本身也有成本。NFA 有 n 个状态时，从数学上可能出现多达二的 n 次方个状态子集，但真实规则的可达状态往往少得多。工程实现可能使用按需状态构造、表压缩或直接模拟 NFA 等方法取舍。要比较它们的价值，应固定词法规范和测试语料，再分别测量生成时间、程序大小、内存和扫描吞吐量。

还需要区别经典 DFA 识别与某些使用回溯的通用正则库。后者对特定模式和输入可能存在非常高的最坏耗时，而集合式 NFA 模拟可以避免许多重复路径枚举。对不可信输入和高性能服务，应该确认底层引擎算法，不是只看工具都叫“正则表达式”就假定复杂度相同。

如果你的课程实验只有几百行源码，优先级应当是：规则清楚、测试完整、错误位置准确、接口稳定。只有这些门槛通过后，再考虑减少状态、改善缓存局部性或者使用更高级的生成器。过早进行复杂优化，常常让本来清楚的自动机学习变成排查工程缺陷的漫长过程。

## 十九、八道检查理解的练习题与答案

**第一题：** 为什么 ifelse 应当是完整标识符？因为标识符规则接受整个词素，最长匹配优先于仅能接受两个字符的关键字 if；只有在输入完整词素恰好等于 if 时，关键字同长优先级才发挥作用。

**第二题：** 为什么 >= 一般不是 GT 与 EQ 两个 Token？因为存在两个字符的合法运算符，按照最长匹配应首先选择 GE。扫描器可以通过前瞻或者记录最近接受状态得到这个结果。

**第三题：** NFA 允许同一个字符走两条边，运行时一定要使用随机数吗？不需要。维护所有可能状态的集合即可；子集构造则进一步把这个集合表示为确定性的 DFA 状态。

**第四题：** 对正规表达式 a(b|c)，输入 abc 为什么不是完整匹配？因为合法字符串只有 ab 与 ac。虽然读完 ab 时达到接受状态，但剩余 c 无法继续消费；完整字符串匹配要求全部输入都被消费。

**第五题：** 为什么经典有限状态机难以直接识别任意深度括号嵌套？因为它没有不受限制的栈或计数空间。词法分析器只输出括号 Token，语法分析器负责递归嵌套结构。

**第六题：** 10..20 扫描错了，应当先改代码还是先明确规则？先明确整数、小数和范围符如何定义及其冲突关系，随后再修改识别器。规范不清时，任何实现都可能在别的输入上再次出现问题。

**第七题：** 空文件触发程序崩溃，应先检查什么？应先检查是否在读取首字符前判断输入结束，以及 EOF 处理是否稳定。重复获取 Token 时不应越过输入边界。

**第八题：** Lexer 生成器能够生成源码，是否证明它拥有通用人工智能？不是。它在明确的正规语言与有限自动机范围内执行已知的结构转换算法；与从模糊自然语言独立完成任意软件设计是两种问题。

## 二十、从课程实验到真实编译器的下一步

掌握本课之后，建议先实现一个支持标识符、整数、小数、双字符运算符和 EOF 的小扫描器，并准备固定的边界输入。第二步手工从 a(b|c) 这样简单的表达式画出 NFA，再用子集构造列出 DFA 状态；第三步用公开词法分析器生成工具写相同规则，比较生成实现和手写实现是否输出相同的 Token 流。

如果两者结果不同，不要急着判断哪一方“算法不好”。先逐项比较源语言规范、最长匹配、规则优先级、数字格式、错误恢复和位置记录，再定位具体差异。生成器能保证的是实现自身被正确配置的规则，不保证我们起初的语言规范没有矛盾。真正有收获的学习方式，是让形式语言理论、可运行代码和反例测试相互验证。

随后就可以进入编译原理的下一章：如何根据上下文无关文法组织 Token、构造表达式语法树、使用递归下降或者 LR 分析处理嵌套结构。再进一步学习符号表、类型检查、中间表示和代码生成。词法分析不是编译器的全部，但它展示了一个非常清楚的工程范式：先定义结构，再用算法变换表示，最后通过可验证程序实现。

### 资料来源与边界

1. [Robert Nystrom, Crafting Interpreters — Scanning](https://craftinginterpreters.com/scanning.html)：用于核对 Token、词素、数字与保留字、最长匹配及扫描器接口。
2. [Cornell CS 4120 编译课程公开笔记](https://www.cs.cornell.edu/courses/cs4120/2026sp/notes/)：用于核对正规表达式、NFA、DFA、自动词法分析与生成器的基本原理。
3. [LLVM — My First Language Frontend Tutorial](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/)：用于理解 Kaleidoscope 的手写扫描器如何衔接语法分析与 LLVM IR。
4. [LLVM Kaleidoscope Tutorial Contents](https://www.llvm.org/docs/tutorial/index.html)：用于核对相关编译器章节的学习顺序。
5. 正则表达式示例、状态编号、三张图、小语言范围符规则及测试样例均为原创教学构造。不同语言可采用不同词法规定，本文不声称所有词法分析器对上述边界文本给出完全一致的结果。

最重要的结论是：词法分析器能够根据一组正规规则自动生成，是因为正则表达式与有限自动机之间存在可以机械执行的转换方法；程序正确性建立在明确语言规范与独立测试之上，而不是建立在生成源码的神奇外观之上。
